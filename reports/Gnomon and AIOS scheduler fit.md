# Gnomon complements AIOS above the syscall

Gnomon and the AIOS kernel documented at docs.aios.foundation both call themselves schedulers, but they schedule different things at time scales three orders of magnitude apart, so Gnomon cannot replace the AIOS scheduler and would make it worse if placed in the per-call path. AIOS dispatches individual LLM, memory, storage and tool syscalls from four in-process FIFO queues inside one Python process; Gnomon places walltime-bounded batch jobs onto cluster nodes with whole-second clocks and second-scale polling. The useful connection is hierarchical: Gnomon as the coarse layer that allocates GPU nodes, model-server replicas and tool-sandbox capacity, with AIOS (or the inference engine) dispatching calls inside that allocation, plus a transfer of Gnomon's design ideas (priority and admission hooks, per-user limits, deterministic replay, shadow policies) into a kernel whose own roadmap has listed priority and multi-LLM scheduling as unbuilt since May 2024. The repository named in the question, The-AIOS/aios, is **not the codebase those docs describe**: it is an unrelated Claude Code productivity framework that shares only the name, has no scheduler, and runs inference remotely; the documented kernel lives at agiresearch/AIOS. On the evidence gathered, Gnomon would have a positive effect on a multi-node, multi-tenant or tool-heavy AIOS deployment, a neutral effect on the single-GPU setup AIOS has been evaluated on, and a negative effect if every syscall were routed through it. None of this has been measured: no published system puts an HPC batch scheduler under an agent framework, and the overhead figures below are estimates from component benchmarks.

## The docs describe agiresearch/AIOS; The-AIOS/aios is a name collision

The first thing to settle is which system the question is about, because the two named sources point at different projects. The documentation at docs.aios.foundation describes an "AIOS Kernel and the AIOS SDK (Cerebrum)" that "provides the AIOS kernel as an abstraction on top of the OS kernel" ([AIOS docs](https://docs.aios.foundation/aios-docs)), which matches agiresearch/AIOS, the "AI Agent Operating System" with 6.5k stars that addresses "scheduling, context switch, memory management, storage management, tool management" ([agiresearch/AIOS](https://github.com/agiresearch/AIOS)). The-AIOS/aios is a separate public repository titled "Amplify yourself and your team – with AI co-workers" ([The-AIOS/aios](https://github.com/The-AIOS/aios)), whose README says "Everyone is building an AIOS. We built **The AIOS**" and whose setup consists of telling Claude Code to install it ([README](https://github.com/The-AIOS/aios/blob/main/README.md)). A search of its whole working tree for `agiresearch`, `aios.foundation` and "LLM Agent Operating System" returned nothing ([tree](https://github.com/The-AIOS/aios)). There is no fork, mirror or shared-code relationship.

The-AIOS/aios is a content-and-scripts framework: of 870 tracked files, **411 are Markdown, 180 shell and 108 Python, with no Rust, C or protobuf** ([tree](https://github.com/The-AIOS/aios)). Its "agents" are Markdown prompt files, its "memory" is a Markdown vault, and its "tools" are bundled MCP servers ([agents/](https://github.com/The-AIOS/aios/tree/main/agents), [mcps/_index.md](https://github.com/The-AIOS/aios/blob/main/mcps/_index.md)). Every session "runs on a Claude model", with a four-rung tier ladder for cost and no local model serving ([MODEL-ROUTING.md](https://github.com/The-AIOS/aios/blob/main/MODEL-ROUTING.md)). It is young and active (120 stars, 28 forks, version 0.8.19, last commit 2026-11-17) and licensed GPL-2.0-or-later ([The-AIOS/aios](https://github.com/The-AIOS/aios), [NOTICE](https://github.com/The-AIOS/aios/blob/main/NOTICE)).

It has no scheduler in the systems sense. Coordination is a file-drop "agent bus": a JSON file in `~/.aios/spawn-inbox/` with the verbs spawn, send, kill and resume, consumed by a running desktop surface, under the stated invariant "Zero inbound surface. If a future design needs a listening port on the agent host, find another way" ([FORTRESS.md](https://github.com/The-AIOS/aios/blob/main/FORTRESS.md)). The same document calls the bus "a single-operator convenience, not a multi-party protocol" because requests carry no authentication. The only concurrency control found is a lock that serialises terminal creation ([install-wrappers.sh](https://github.com/The-AIOS/aios/blob/main/hooks/claude-identity/install-wrappers.sh)), and timed work is handed to launchd, systemd timers or Task Scheduler ([hooks/_index.md](https://github.com/The-AIOS/aios/blob/main/hooks/_index.md)).

So The-AIOS/aios plays almost no part in a Gnomon fit analysis. Its schedulable quantities are session count, subscription rate-limit headroom and model tier, none of which is a resource Gnomon models, and Gnomon's gRPC, controller-and-agent design runs directly against the project's no-listener rule. The only conceivable seam is an adapter that writes spawn-inbox files, which would use Gnomon as an elaborate cron. The rest of this report therefore treats "the AIOS architecture" as agiresearch/AIOS. One caveat on this section: the GitHub API was unreachable during research, so The-AIOS/aios issues and pull requests were not checked for scheduling discussions.

## AIOS schedules syscalls in one Python process, with FIFO and a broken round robin

The documented AIOS scheduler is small. The docs say "we centralize all the queues within the scheduler module" and serve agents at "syscall level" granularity ([AIOS docs: scheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler)). In code, that is four global standard-library `queue.Queue` objects (LLM, memory, storage, tool), unbounded and FIFO, with one dispatcher thread each ([_global.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/stores/_global.py), [queue.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/stores/queue.py), [base.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/base.py)). Agents are not scheduled at all: they are threads in a pool with a default of 64 workers that block on each syscall ([agent.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/modules/agent.py)). Each syscall carries a `priority` field that the docs advertise as "Priority Handling", but nothing in the repository reads it for dispatch ([syscall/__init__.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/__init__.py), [AIOS docs: syscalls](https://docs.aios.foundation/aios-docs/aios-kernel/syscalls)).

Exactly two policies ship, FIFO and Round Robin ([aios/scheduler](https://github.com/agiresearch/AIOS/tree/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler)), and there is no selector: the kernel uses RR when `llms.use_context_manager` is true and FIFO otherwise ([launch.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch.py)). The docs and the code have drifted apart. The docs, whose kernel pages all read "Last updated 1 year ago", describe FIFO as having "a 1-second timeout for each task" ([AIOS docs: FIFOScheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler/fifoscheduler)); in the current code the one second is a batching window, after which every queued LLM request is sent to its backend concurrently with no cap ([fifo_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/fifo_scheduler.py), [adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py)). Round robin's "preemption" is cooperative: the LLM worker checks a wall clock between stream chunks or decode steps and returns early, saving partial text for API backends or the KV cache for in-process HuggingFace models ([simple_context.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/context/simple_context.py)). On current `main` the **RR path raises a `TypeError` and kills its dispatcher thread**, a bug reported in July 2025 and still reproducing in November 2026 ([issue #504](https://github.com/agiresearch/AIOS/issues/504), [PR #560](https://github.com/agiresearch/AIOS/pull/560)).

The published performance case is narrower than the headline suggests. On a single RTX A5000 with "a single LLM deployed that can process only one prompt request at a time", the paper reports up to 2.1x throughput over agent frameworks without AIOS, and attributes it to scheduling "which prevents unnecessary trial-and-error attempts by avoiding prompts that cannot be loaded onto the GPU" ([AIOS paper](https://arxiv.org/html/2403.16971v4)). The one ablation that compares policies shows the policy barely matters in that setup:

| Strategy | Overall execution time (s) | Avg. agent wait (s) | p90 agent wait (s) |
| --- | --- | --- | --- |
| None (no AIOS) | 152.1 | 9.8 | 11.0 |
| FIFO | 74.2 | 3.0 | 5.0 |
| RR | 77.3 | 3.2 | 4.2 |

Source: Table 6, ReAct agents on HumanEval with Llama-3.1-8b ([AIOS paper](https://arxiv.org/html/2403.16971v4)). The gain comes from having any admission queue in front of a one-at-a-time GPU; FIFO and RR differ by about 4%. A more sophisticated policy has nothing to act on in a homogeneous, single-engine workload.

The gaps are acknowledged by the project itself. The roadmap issue opened in May 2024 and still open lists "Priority-based Agent-level Scheduling", "Multi-core AIOS based on Multi-LLM Scheduling" and "Efficiency-based Prompt-level Scheduling" as to-do ([issue #127](https://github.com/agiresearch/AIOS/issues/127)). A September 2026 feature request states "There is no way to mark an agent as urgent, no way to guarantee an agent a minimum share of LLM capacity, and no way to select a scheduling policy" ([issue #554](https://github.com/agiresearch/AIOS/issues/554)). A backend rate-limit error is returned to the agent as a finished 429 response with no backoff or retry in the scheduler ([adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py)). All state is in process memory, so the kernel is single-node and loses queued work on restart; of the five deployment modes in the docs, only local and remote kernel are supported, and the multi-user modes that would need "scheduling and resource allocation mechanism for different virtual machines" are unbuilt ([AIOS docs](https://docs.aios.foundation/aios-docs), [README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)). The repository also contains an experimental Rust scaffold, `aios-rs`, whose scheduler is a trait with `start`/`stop` and a `NoopScheduler` ([aios-rs/src/scheduler.rs](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios-rs/src/scheduler.rs)).

## Gnomon plans batch jobs in whole seconds and cannot preempt

Gnomon sits at the opposite end of the scheduling spectrum. It describes itself as "A Rust-native HPC scheduler" and "a research codebase" ([README.md](../README.md)), built on the idea that "scheduling is managing the time axis": every schedulable vertex of a resource graph carries a planner of running spans and future reservations, the scheduler plans against immutable snapshots, and a single applier commits with per-vertex optimistic concurrency ([docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md)). Its unit of work is a `Job`: a shell command or container image with a per-node request for cores, memory and GPUs, a walltime, a scalar priority and an optional multi-node gang size ([crates/core/src/lib.rs](../crates/core/src/lib.rs)). The policy is priority-ordered conservative backfill with earliest-fit placement and all-or-nothing gang matching ([crates/sched/src/lib.rs](../crates/sched/src/lib.rs)).

Four properties of that design decide the AIOS question, and each one cuts against using Gnomon for LLM syscalls.

**Time granularity.** The clock is whole Unix seconds and walltime is clamped to at least one second ([crates/core/src/lib.rs](../crates/core/src/lib.rs), [crates/api/src/lib.rs](../crates/api/src/lib.rs)). The backfill pass runs every second and node agents pull work on a poll of two seconds or more; the controller never dials out ([crates/ctl/src/main.rs](../crates/ctl/src/main.rs), [crates/agent/src/main.rs](../crates/agent/src/main.rs)). An AIOS syscall that reached an executor through this path would wait seconds for delivery, while the AIOS ablation above measures average agent waits of about three seconds in total.

**No preemption.** The job state enum has no suspended state and the event enum has no preemption event; a running job ends by completion, walltime, cancellation, peer failure or node loss ([crates/core/src/lib.rs](../crates/core/src/lib.rs)). AIOS's only differentiating scheduling mechanism, time-sliced context switching of generation, has no counterpart.

**A closed resource model.** `Resources` is a fixed struct of `cores`, `mem_mb` and `gpus`, mirrored in the gRPC message ([crates/core/src/lib.rs](../crates/core/src/lib.rs), [proto/gnomon.proto](../proto/gnomon.proto)). There is no named consumable for tokens per minute, API rate limits or model-server concurrency slots, and GPUs are an undifferentiated count per node with no type, memory size or sharing. Fair-share accounting is listed in the README roadmap as "next" ([README.md](../README.md)).

**Backfill needs runtime bounds.** The whole placement algorithm depends on a walltime per job. The LLM-serving literature treats output length as "not known a priori" and falls back on rank prediction or attained-service ordering instead ([Learning to Rank](https://arxiv.org/abs/2408.15792), [Autellix](https://arxiv.org/html/2502.13965v1)). No published evaluation of backfill on LLM request queues was found.

What Gnomon does well is real and relevant at a coarser grain. Its full controller path measured **1,825 to 3,151 job decisions per second** on a two-core sandbox ([results/EVALUATION.md](../results/EVALUATION.md)), far above the syscall rate of an AIOS instance on one GPU. It has opt-in Raft replication with a durable log, which AIOS lacks entirely ([docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md)). Its time-varying capacity profiles produced zero cap violations with 85% lower median wait than static derating under a power cap ([results/EVALUATION.md](../results/EVALUATION.md)). Policy is extensible through sandboxed WASM hooks for admission, priority, runtime estimate and node score, at roughly 10 to 35 microseconds per call ([crates/policy/wit/policy.wit](../crates/policy/wit/policy.wit), [ADR 0004](../.github/plans/0004-node-score-plugins.md)). A 132,421-event journal replays to bit-identical state, and a `ShadowPolicy` runs a candidate beside the live policy and records disagreements without applying them ([results/EVALUATION.md](../results/EVALUATION.md), [crates/sched/src/lib.rs](../crates/sched/src/lib.rs)). And the planning core (`gnomon-core`, `-graph`, `-fsm`, `-sched`) is synchronous Rust depending only on `serde`, already used as a library by the simulator ([docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md)).

Maturity is a constraint on both sides. Gnomon is at 10 commits and version 0.5.0, its benchmarks ran on a two-core sandbox or a four-vCPU VM, its API has no authentication, and its repository contains no feature aimed at LLM or agent workloads beyond counting GPUs ([README.md](../README.md), [proto/gnomon.proto](../proto/gnomon.proto), [results/EVALUATION.md](../results/EVALUATION.md)).

## Three connections are plausible, and only the coarse ones pay

Putting the two profiles side by side shows where a connection can exist.

| Dimension | AIOS kernel (agiresearch) | Gnomon |
| --- | --- | --- |
| Scheduled unit | One LLM, memory, storage or tool syscall | One batch job (command or container) on one or more nodes |
| Time scale | Sub-second to seconds per unit | Seconds to hours; whole-second clock |
| Policies | FIFO; RR (broken on `main`) | Priority-ordered conservative backfill, gang placement |
| Preemption | Cooperative time slice with context save | None |
| Resources modelled | None (no GPU, token or rate-limit model) | Cores, memory, GPU count per node, capacity over time |
| Runtime | One Python process, threads, in-memory | Rust controller and node agents, gRPC, optional Raft |
| Extension point | Subclass `BaseScheduler`, edit launch code | `Policy` trait, four WASM hooks |

Sources: AIOS rows from the [scheduler docs](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler) and [kernel code](https://github.com/agiresearch/AIOS/tree/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler); Gnomon rows from [docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md) and [crates/sched/src/lib.rs](../crates/sched/src/lib.rs).

### Connection one: Gnomon below AIOS, allocating the machines AIOS runs on

This is the connection with precedent. AIOS expects model servers to be started separately (for example `vllm serve` on its own port) and treats each as a "core" ([config.yaml.example](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/config/config.yaml.example)). Launching and placing those servers, kernel instances and GPU-bound tool models across a cluster is ordinary batch-scheduler work: long-lived jobs with GPU counts and walltimes, which is exactly what Gnomon's job model expresses. Everywhere fine-grained work has been run on batch systems, the pattern is two-level. A benchmark of Slurm, Grid Engine, Mesos and YARN found utilisation below 10% for computations lasting a few seconds, restored to above 90% by a multilevel layer that aggregates short tasks ([Reuther et al.](https://arxiv.org/abs/1705.03102)). On Frontier, Slurm's `srun` peaked at 152 tasks per second while a pilot layer over Flux sustained 930 ([RADICAL-Pilot study](https://arxiv.org/abs/2509.20819)). In this arrangement AIOS is the task layer and Gnomon grants it leases. Gnomon's subgraph delegation, where a parent hands a set of nodes to a child scheduler, is the matching mechanism, though it is in-process only today with cross-process children listed as future work ([crates/graph/src/lib.rs](../crates/graph/src/lib.rs), [README.md](../README.md)).

### Connection two: Gnomon beside AIOS, running tool and sandbox work

AIOS handles tool syscalls one at a time on a single dispatcher thread, so a slow tool call blocks every other agent's tool calls ([base.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/base.py)), and its computer-use variant drives Docker and cloud VMs through the tool manager ([README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)). The agent-systems literature shows this side matters: in a study of 144 coding tasks, OS-level execution (tool calls plus container and agent initialisation) was **55 to 60% of end-to-end latency**, with memory rather than CPU the concurrency bottleneck ([AgentCgroup](https://arxiv.org/abs/2602.09345)). Heavy tool work (builds, test suites, sandboxes with declared CPU and memory limits) looks like Gnomon jobs: cgroup-confined, containerised, seconds to minutes long. Dispatching those through Gnomon's gRPC API would give them multi-node capacity, per-user limits and isolation AIOS lacks. The fit is partial. The same study measured tool memory spikes at up to 15.4x peak-to-average and calls demand "highly unpredictable", which static per-job requests in the batch style handle poorly, and Gnomon's two-second dispatch floor rules it out for short tool calls.

### Connection three: Gnomon's ideas inside the AIOS scheduler

The third connection is a transfer of design, not a deployment. AIOS's custom-scheduler seam is workable: a `BaseScheduler` subclass is the sole consumer of the queues and can reorder, hold back or rate-limit using `agent_name`, `pid`, `created_time` and the unused `priority` field ([base.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/base.py)). Several Gnomon components map onto what issue #554 asks for: the `EvalBroker` ordering (priority descending, FIFO within a priority), declarative priority weights with aging, per-user limits and an admission hook that can accept, reject or rewrite a request ([crates/sched/src/lib.rs](../crates/sched/src/lib.rs), [crates/policy/src/lib.rs](../crates/policy/src/lib.rs)). Gnomon's replay and shadow-policy machinery would also give AIOS something it has never had: the first scheduler tests arrived only in a draft pull request in November 2026 ([PR #560](https://github.com/agiresearch/AIOS/pull/560)). The Rust scaffold in `aios-rs` is a natural landing place for crates that depend only on `serde`, but this is inference; nothing in either repository proposes it, Gnomon publishes no Python bindings, and the AIOS maintainers have not responded to any of the three community scheduler threads opened in 2026.

Two Gnomon concepts need rework before they carry over. Fair-share must be accounted in tokens, not core-seconds, to be meaningful under continuous batching ([VTC](https://arxiv.org/abs/2401.00588)), and Gnomon has no fair-share history yet. Rate limits could be approximated by a synthetic node with a periodic capacity profile, but a profile is a ceiling on concurrent usage, not a cumulative token budget, so this is a workaround and not a model.

### The connection that fails: Gnomon in the per-syscall path

Routing each AIOS syscall through Gnomon as a job is the literal reading of "use Gnomon as the AI OS scheduler", and it is the one arrangement the evidence argues against. The delivery floor of seconds exceeds the waits AIOS already achieves. The systems that beat FIFO for agent workloads do it with signals an external batch scheduler cannot see: Autellix reports 4 to 15x program throughput by scheduling on per-program attained service inside the vLLM batch loop, and Continuum reports over 8x better job completion time by pinning an agent's KV cache across tool calls ([Autellix](https://arxiv.org/html/2502.13965v1), [Continuum](https://arxiv.org/abs/2511.02230)). Naive policies in front of an engine can be net negative: call-level multi-level feedback queues ran out of memory at 4,000 programs, and fairness that ignores prefix locality cost up to 2.87x throughput ([Autellix](https://arxiv.org/html/2502.13965v1), [DLPM](https://arxiv.org/abs/2501.14312)). Even with Gnomon's polling removed by embedding the core in-process, the planner still works in integer seconds and each evaluation clones the full state ([crates/fsm/src/lib.rs](../crates/fsm/src/lib.rs)).

## The net effect is positive only for multi-node, multi-tenant or tool-heavy AIOS

Whether Gnomon would make a positive impact depends on which AIOS deployment is in view, and the answer differs sharply across three cases.

For the deployment AIOS has actually been built and measured on (one kernel process, one GPU or one Ollama server, homogeneous agents), the effect is **neutral to negative**. There is one engine, so there is nothing to place; FIFO and RR are 4% apart, so there is little ordering gain to capture; and a default install already delegates LLM scheduling to the Ollama server because FIFO releases each batch with unbounded concurrency ([config.yaml.example](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/config/config.yaml.example), [fifo_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/fifo_scheduler.py)). Adding a controller, node agents and a Raft log to a single-node workload buys operational burden and no throughput; high availability for the scheduler is worth little while the kernel itself is a single point of failure.

For API-backed agents, the effect is **neutral**. The binding constraints are provider rate limits and cost, the engine queue is outside anyone's control, and Gnomon has no token or rate-limit resource. An analysis of more than 40,000 issues across six agent frameworks identified blocking, zombie processes and rate-limit cascades as the scheduling failures users hit, and reported 86% lower P95 latency from a rate-limit-aware admission layer ([AgentRM](https://arxiv.org/abs/2603.13110)). That niche is real, but it is filled by a lightweight in-process admission controller, not a cluster scheduler.

For a multi-node, multi-tenant AIOS (several GPU nodes, several model servers, many users, heavy sandboxed tools), the effect is **positive, with engineering work on both sides**. This is the configuration behind AIOS's unbuilt "Multi-LLM Scheduling" roadmap item and its unbuilt per-user kernel modes, and it is where Gnomon's strengths apply directly: GPU-count placement across nodes, per-user core and GPU limits, capacity profiles, replicated state, and auditable policy. The gain here is capability AIOS does not have at all (running across a cluster, surviving a controller failure, enforcing quotas), not a speed-up of something it already does. Reaching it requires AIOS to treat model-server endpoints as dynamic and Gnomon to gain cross-process delegation, an authenticated API and, for accounting, a consumable beyond cores, memory and GPU count.

The steelman for a stronger claim is that Gnomon's optimistic planning core is fast enough (hundreds of thousands of decisions per second on small problems, per [bench_results.csv](../bench_results.csv)) that a purpose-built event-driven front end could serve syscalls directly. That is true of decision throughput and beside the point: the published gains for LLM scheduling come from engine-internal state and program structure, and the cadence, clock and job model would all have to be replaced to use them, at which point what remains of Gnomon is its concurrency scheme and test harness.

Several things remain unknown. No one has benchmarked Gnomon and AIOS together, so every effect above is reasoned from component evidence. A rough budget of 1.5 to 3 milliseconds per call for a gRPC round trip plus one replicated log write is an estimate assembled from old, hardware-specific figures such as the 1.6 ms unloaded write latency in etcd's v3.3 benchmark ([etcd performance](https://etcd.io/docs/v3.3/op-guide/performance/)); Gnomon reports no latency percentiles, no Raft failover timing and no replicated-mode throughput ([results/EVALUATION.md](../results/EVALUATION.md)). The AIOS docs are about a year stale relative to the code, the Cerebrum SDK was not examined, and the search that found no HPC scheduler in an agent framework's call path covered roughly fifteen queries, which is absence of evidence only.

## Conclusion

The question assumes Gnomon and the AIOS scheduler are candidates for the same slot, and the research shows they are layers of a stack that neither project has built. AIOS's scheduler is an admission queue that stops many agents from overrunning one model; its measured value is the queue itself, and its open problems (priority, fair-share, policy selection, multi-model placement, rate limits) are split between things best solved inside the Python kernel or the inference engine and things that need a cluster resource manager. Gnomon is a candidate for the second group only. The practical order of work follows from that split: fix and extend the AIOS scheduler in place, borrowing Gnomon's priority, admission and replay designs, and bring Gnomon in when an AIOS deployment first spans more than one GPU node or more than one tenant.

The most reusable asset Gnomon offers an AI OS is not backfill but its verification discipline. A scheduler whose round-robin path has been broken on `main` for over a year without tests benefits more from deterministic replay and shadow evaluation than from any new policy, and that transfer costs nothing in latency. For The-AIOS/aios the conclusion is simpler: it is a different product with the same name, and anyone following the docs.aios.foundation architecture should be working from agiresearch/AIOS.
