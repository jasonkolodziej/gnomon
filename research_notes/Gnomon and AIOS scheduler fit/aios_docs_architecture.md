## What exactly does the AIOS scheduler schedule (LLM syscalls, memory/storage/tool syscalls, agent threads)? What queues and data structures does it use?

### Takeaway
The scheduler schedules individual **syscalls** (LLM, memory, storage, tool), not agents: it owns four global in-process FIFO `queue.Queue`s, one per module, and runs one dispatcher thread per queue. Agents are not scheduled at all; they are plain threads in a `ThreadPoolExecutor` (or remote HTTP clients) that block on each syscall until the scheduler completes it.

### Cited Findings

#### Architecture context (layers and kernel modules)
- AIOS "includes the AIOS Kernel and the AIOS SDK (Cerebrum)" and "provides the AIOS kernel as an abstraction on top of the OS kernel"; the SDK sits on top of the kernel layer. — [Docs: index](https://docs.aios.foundation/aios-docs)
- The paper describes an application layer (agents built on the SDK), a kernel layer that "integrates two components: the traditional OS kernel for non-LLM computing tasks and our innovative AIOS kernel", and a hardware layer; "AIOS kernel does not directly interact with the hardware but relies on OS system calls to access the physical resources". — [Paper v4](https://arxiv.org/html/2403.16971v4)
- Kernel modules named by docs and paper: LLM Core(s), Scheduler, Context Manager, Memory Manager, Storage Manager, Tool Manager, Access Manager. — [Docs: kernel overview](https://docs.aios.foundation/aios-docs/aios-kernel/overview); [Paper v4](https://arxiv.org/html/2403.16971v4)
- LLM Core: "wraps the deployed instances of LLM from different providers in a unified manner, treating each LLM as a core similar to CPU cores". — [Docs: kernel overview](https://docs.aios.foundation/aios-docs/aios-kernel/overview)
- Context = data fed to the LLM core while it is processing; Memory = transient data in RAM, "cleared after tasks complete"; Storage = persistent data on disk. — [Docs: kernel overview](https://docs.aios.foundation/aios-docs/aios-kernel/overview)
- Tool Manager "manages tool call conflicts and prioritizes tool operations"; the paper adds parameter validation before execution and "conflict resolution hashmaps". — [Docs: kernel overview](https://docs.aios.foundation/aios-docs/aios-kernel/overview); [Paper v4](https://arxiv.org/html/2403.16971v4)
- Access Manager: privilege groups in a hashmap from agent ID to group, plus a user-confirmation prompt for irreversible operations. The docs mark static and dynamic access control lists "(TBD)" and say the module "is still under development". — [Docs: access](https://docs.aios.foundation/aios-docs/aios-kernel/access)
- Access-manager syscalls are not dispatched by the scheduler ("We omit the access manager module here as the access-related system calls will not be dispatched by the scheduler"). — [Paper v4, Fig. 3 caption](https://arxiv.org/html/2403.16971v4)
- The context manager is likewise not scheduled: it "will be triggered within LLM core for handling context interruptions instead of being scheduled". — [Paper v4, §3.1](https://arxiv.org/html/2403.16971v4)
- Paper Table 2 lists the syscalls per module: LLM Core (`execute_llm_syscall`, `get_model_response`, `process_model_response`), Scheduler (`execute_syscall`, `start`, `stop`), Context Manager (`generate_response_with_interruption`, `load_context`, `clear_context`), Memory (`add_memory`, `remove_memory`, `update_memory`, `retrieve_memory`), Storage (`sto_create_file`, `sto_create_directory`, `sto_mount`, `sto_write`, `sto_retrieve`, `sto_rollback`, `sto_share`), Tool (`execute_tool_syscall`, `load_tool_instance`), Access (`add_privilege`, `check_access`, `ask_permission`). — [Paper v4, App. A.1](https://arxiv.org/html/2403.16971v4)
- SDK to kernel transport: all SDK queries "are ultimately channeled through a central `send_request(Query)` function ... which then communicates with the AIOS kernel via HTTP requests (either to localhost or a remote URL)". — [Docs: SDK overview](https://docs.aios.foundation/aios-docs/aios-agent-sdk/overview)

#### What is scheduled
- Docs: "we centralize all the queues within the scheduler module" instead of per-module queues; the scheduler serves agents "in a fine-grained granularity (i.e., syscall level granuity)". — [Docs: scheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler)
- Docs say the request queue "includes both Queries (agent-to-kernel request) and Messages (module-to-module request)". — [Docs: scheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler)
- Paper: agent queries are decomposed into four syscall categories (LLM processing, memory access, storage operations, tool usage); "Each syscall is thread-bound and dispatched by the scheduler"; each module monitors its designated queue. — [Paper v4, §3.1](https://arxiv.org/html/2403.16971v4)
- Code: `BaseScheduler.__init__` takes the four module objects (`llm: LLMAdapter`, `memory_manager`, `storage_manager`, `tool_manager`) and four queue-getter callables (`get_llm_syscall`, `get_memory_syscall`, `get_storage_syscall`, `get_tool_syscall`). `start_processing_threads` starts one `threading.Thread` per processor function. — [Code: aios/scheduler/base.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/base.py)

#### Queues and data structures
- Code: four module-level global queues (`global_llm_req_queue`, `global_memory_req_queue`, `global_storage_req_queue`, `global_tool_req_queue`) are created at import time. — [Code: aios/hooks/stores/_global.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/stores/_global.py)
- Code: each is a standard-library `queue.Queue` (unbounded FIFO). `getMessage` is `q.get(block=True, timeout=0.1)`; `addMessage` is `q.put(message)`. There is no priority queue, no per-agent queue and no size limit. — [Code: aios/hooks/stores/queue.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/stores/queue.py)
- Code: a `Syscall` is a `threading.Thread` subclass whose `run()` is just `self.event.wait()`. It carries `agent_name`, `query`, `event`, `pid`, `aid`, `status`, `response`, `time_limit`, `created_time`, `start_time`, `end_time`, `source`, `target`, `priority`. — [Code: aios/syscall/__init__.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/__init__.py); [Docs: syscalls](https://docs.aios.foundation/aios-docs/aios-kernel/syscalls)
- Code: the `priority` field has a setter and getter but a repository-wide search finds no reader in `aios/scheduler/` or anywhere else that affects dispatch. The docs nevertheless list "Priority Handling: Allows prioritization of system calls" as a Syscall feature. — [Code: aios/syscall/__init__.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/__init__.py); [Docs: syscalls](https://docs.aios.foundation/aios-docs/aios-kernel/syscalls)
- Code, request path: `SyscallExecutor._execute_syscall` builds a typed syscall (`LLMSyscall`, `StorageSyscall`, `MemorySyscall`, `ToolSyscall`) from the query type, stamps `created_time` and a monotonically increasing integer `pid` (one per logical request, under a lock), puts it on the matching global queue, then calls `syscall.start(); syscall.join()`. The caller thread is therefore blocked until a scheduler thread sets `syscall.event`. It returns the response plus lists of `start_times`, `end_times`, `waiting_times` (`start - created`) and `turnaround_times` (`end - created`). — [Code: aios/syscall/syscall.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/syscall.py)
- Code: the HTTP entry point is FastAPI `POST /query` with `query_type` in `llm | tool | storage | memory`. LLM queries run via `asyncio.to_thread(execute_request, ...)`; storage, tool and memory queries call `execute_request` directly inside the `async` handler. — [Code: runtime/launch.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch.py)

#### Agents
- Code: agents submitted through `POST /agents/submit` run in a `ThreadPoolExecutor(max_workers=params.max_workers)`; the default is `agent_factory.max_workers: 64` in the example config. Each gets a random 6-digit process id. The pool is plain FIFO submission; nothing in the scheduler orders or preempts agent threads. — [Code: aios/hooks/modules/agent.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/modules/agent.py); [Code: config.yaml.example](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/config/config.yaml.example)

### Inferences
- The unit of scheduling is one kernel request (one LLM call, one tool call, etc.). There is no kernel object for an agent run, a task, a DAG or a deadline, so anything above syscall granularity (agent priority, fair share per agent or per user, dependency ordering) has nowhere to live in the current data model except the unused `priority` field and `agent_name` string.
- The four queues are independent, so the four syscall classes never compete with each other in the scheduler; contention only exists inside one class (in practice the LLM queue).
- Memory, storage and tool syscalls are handled strictly one at a time per class (one dispatcher thread, synchronous executor call), so a slow tool call blocks every other agent's tool calls. LLM syscalls are the only class with any concurrency (see next question).
- Because storage/tool/memory `/query` handlers call the blocking `execute_request` directly in an `async def`, they appear to block the FastAPI event loop while waiting. I did not run the server to confirm the practical effect.
- The docs' "Messages (module-to-module request)" has no obvious counterpart in the code I read: only agent-originated queries are enqueued by `SyscallExecutor`. Treat it as a docs claim.

### Gaps
- I did not read the Cerebrum SDK repository or the Cerebrum paper (arXiv 2503.11444, NAACL 2025) beyond the docs' SDK overview page, so SDK-side details (retry behaviour, client timeouts, how agents are packaged) are not covered here.
- The docs pages for memory, storage and tools were not read in detail; the notes above rely on the kernel overview page and the paper for those modules.

## Which scheduling algorithms are implemented (FIFO, Round Robin, others)? How is preemption/context switching of LLM generation done (context manager, time slices)?

### Takeaway
Exactly two schedulers ship: `FIFOScheduler` and `RRScheduler`. "Preemption" is cooperative, wall-clock based and lives in the LLM adapter's `SimpleContextManager` (1-second slice; streamed text is saved for API backends, KV cache and generated tokens for local HuggingFace models), and on current `main` the RR scheduler's LLM path is broken by an open bug (#504).

### Cited Findings

#### What ships
- Docs comparison table: FIFO = first-come first-served, no time limit, no preemption, statuses "executing"/"done", no context management. RR = round-robin rotation, fixed time slices, tasks can be suspended and resumed, statuses "executing"/"done"/"suspending", uses `SimpleContextManager`. — [Docs: scheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler)
- Paper §3.3: "we implement two classic algorithms: First-In-First-Out (FIFO) ... and Round Robin (RR)". Appendix A.3 says schedulers "implementing algorithms such as FIFO, Round Robin, and priority-based scheduling can be derived from this base class". — [Paper v4](https://arxiv.org/html/2403.16971v4)
- Code: `aios/scheduler/` contains only `base.py`, `fifo_scheduler.py`, `rr_scheduler.py` and an `__init__.py` with commented-out imports. No priority scheduler exists. — [Code: aios/scheduler](https://github.com/agiresearch/AIOS/tree/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler)
- An experimental Rust scaffold `aios-rs/` defines a `Scheduler` trait with only `start`/`stop` and a `NoopScheduler`; its README lists "Port scheduling strategies (FIFO, RR) with test parity" as a roadmap goal, with "No async runtime yet". It was added in PR #505 (merged 2025-08-13). — [Code: aios-rs/src/scheduler.rs](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios-rs/src/scheduler.rs); [Code: aios-rs/README.md](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios-rs/README.md)

#### FIFO as implemented (differs from the docs)
- Docs: FIFO "processes tasks in the order they arrive, with a 1-second timeout for each task". — [Docs: FIFOScheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler/fifoscheduler)
- Code: the class docstring says "LLM tasks are batched based on a time interval. Other tasks (Memory, Storage, Tool) are processed individually as they arrive." `process_llm_requests` sleeps `batch_interval` (constructor default `1.0` s; the docstring says 0.1), then drains the whole LLM queue into a list and calls `self.llm.execute_llm_syscalls(batch)`. The 1 second is a batching window, not a per-task timeout; no time limit is set on FIFO syscalls. — [Code: aios/scheduler/fifo_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/fifo_scheduler.py)
- Code: `LLMAdapter.execute_llm_syscalls` routes each syscall in the batch to a model index, groups by model, and runs the groups in a `ThreadPoolExecutor(max_workers=len(groups))`; inside each group `_process_batch_for_model` uses another `ThreadPoolExecutor(max_workers=len(tasks))`. Every LLM request in a batch is therefore sent to its backend concurrently, with no cap. — [Code: aios/llm_core/adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py)
- Code: the dispatcher thread waits for the entire batch to finish before sleeping and collecting the next batch. — [Code: aios/scheduler/fifo_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/fifo_scheduler.py)

#### Round Robin as implemented
- Docs: "Configurable time slice per task (default: 1 second)", "Preemptive scheduling", "Support for suspending and resuming long-running tasks". — [Docs: RRScheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler/rrscheduler)
- Code: `RRScheduler.__init__(self, *args, time_slice: float = 1, **kwargs)`. `_execute_batch_syscalls` calls `syscall.set_time_limit(self.time_slice)` on each syscall before handing it to the LLM adapter. The scheduler also instantiates its own `SimpleContextManager`, but that attribute is not referenced again in the file; the context manager that actually runs is the one inside `LLMAdapter`. — [Code: aios/scheduler/rr_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/rr_scheduler.py)
- Code: rotation is produced by the caller, not the scheduler. If the returned status is not `"done"`, the `while True` loop in `SyscallExecutor._execute_syscall` creates a new syscall object for the same query with the same `pid` and puts it at the tail of the queue again. The saved context is found by `pid`. — [Code: aios/syscall/syscall.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/syscall.py)
- Code: `time_slice` is not passed from `runtime/launch.py` or read from `config.yaml`, so it is fixed at the 1-second default unless the code is edited. The same is true of FIFO's `batch_interval`. — [Code: runtime/launch.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch.py)
- **Open bug**: `RRScheduler.process_llm_requests` passes a single syscall to `_execute_batch_syscalls`, which iterates it and raises `TypeError: 'LLMSyscall' object is not iterable`, killing the `process_llm_requests` thread. Reported in issue #504 (2025-07-29) with `use_context_manager: true`. A maintainer replied on 2025-11-15 that fixes had been made, but the code at `292d98f7` still has the bug, and draft PR #560 (opened 2026-11-07) states "This still reproduces on main at `292d98f7`". — [Issue #504](https://github.com/agiresearch/AIOS/issues/504); [PR #560](https://github.com/agiresearch/AIOS/pull/560); [Code: aios/scheduler/rr_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/rr_scheduler.py)
- PR #560 adds the first scheduler tests (`tests/modules/scheduler/test_rr_scheduler.py`); the author notes they "do not validate actual model interruption/resumption". At `292d98f7` the `tests/modules/` directory has no scheduler tests. — [PR #560](https://github.com/agiresearch/AIOS/pull/560)
- Status strings are inconsistent: docs say `"suspending"`, the adapter sets `"suspend"` for unfinished responses and `"error"` for a failed worker group, and the executor loop only exits on `"done"`. — [Docs: RRScheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler/rrscheduler); [Code: aios/llm_core/adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py); [Code: aios/syscall/syscall.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/syscall.py)

#### Context switching of LLM generation
- Paper §3.4: two approaches, "text-based (for closed-source LLMs without logits access, saving decoded outputs) and logits-based (preserving intermediate search tree structure for finer-grained state restoration)". When "suspended by the scheduler mid-generation, the context manager snapshots the intermediate results" and reloads on resumption. — [Paper v4](https://arxiv.org/html/2403.16971v4)
- Docs: text-based switching is "Compatible with API-based models and OpenAI clients" and "Uses streaming responses with partial content accumulation"; logits-based is "Currently only supported for HuggingFace models" and "Saves generated tokens, past key values, and other state information". — [Docs: context](https://docs.aios.foundation/aios-docs/aios-kernel/context)
- Code, text-based: `process_completion_streaming_response` iterates the stream, appends deltas, and after each chunk checks `time.time() - start_time > time_limit`; if exceeded and `finish_reason is None`, it breaks and returns `finished=False`. The accumulated text is stored in `context_dict[str(pid)]`. — [Code: aios/context/simple_context.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/context/simple_context.py)
- Code, logits-based: `generate_with_time_limit_hf` runs a token loop, checks the wall clock each step, and saves `past_key_values` plus generation state into `context_dict[str(pid)]`. — [Code: aios/context/simple_context.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/context/simple_context.py)
- Code: tool-call requests are made with `stream=False` ("Don't stream tool calls"), so they cannot be interrupted by the time limit. — [Code: aios/context/simple_context.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/context/simple_context.py)
- Code: the context manager is only used when `use_context_manager` is true (`_get_model_response` branches on `self.use_context_manager and self.context_manager`); otherwise the adapter makes an ordinary blocking completion call. — [Code: aios/llm_core/adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py)
- Paper Table 7: outputs with and without context switching were identical (BLEU 1.0, BERTScore 1.0) for text-based and logits-based methods on Mistral-7B and Llama-3-8B. — [Paper v4, App. D.2](https://arxiv.org/html/2403.16971v4)

### Inferences
- Preemption is not asynchronous interruption of a running generation by the scheduler. The LLM worker checks a clock between stream chunks or decode steps and voluntarily returns. A backend that stalls before its first chunk, or a non-streamed tool call, holds its worker for the full call.
- For API and OpenAI-compatible backends, "suspending" means the client stops reading the stream. The code I read stores only the partial text; how the resumed request continues from it (for example by re-sending the partial text as a prefix) was not traced. Whether the remote server keeps generating, and who pays for discarded tokens, is outside AIOS's control.
- "Round robin" here is requeue-at-tail of unfinished requests in one FIFO queue. With the intended one-syscall-per-dispatch RR loop and a synchronous adapter call, RR would serve one LLM request at a time per dispatcher, in contrast to FIFO's batch-concurrent behaviour. This is a reading of the code, not a measured result, and the RR path currently crashes before reaching the adapter.
- Syscalls whose worker group fails get status `"error"` with a `finished=True` response; since the executor loop only breaks on `"done"`, such a request looks like it would be re-enqueued repeatedly. I did not execute this path.
- The paper's evaluation used RR by default (see the results question), so the published numbers come from an earlier revision in which RR worked; that revision was not identified.

### Gaps
- I could not determine which commit introduced the RR regression or the LLM batching in FIFO (the clone was shallow). The FIFO batching is absent from the docs (March 2025), so it post-dates them.
- No documentation or code was found for any algorithm other than FIFO and RR (no priority, SJF, MLFQ, EDF, fair-share or lottery scheduler).

## How is a scheduler selected/configured, and is there a documented interface for custom schedulers? What language/runtime is it (Python threads?), single-node or distributed?

### Takeaway
There is no scheduler selector: the kernel picks RR when `llms.use_context_manager` is true and FIFO otherwise, and the only `scheduler:` config key is `log_mode`. The extension point is subclassing the Python `BaseScheduler` ABC and editing the launch code by hand; the runtime is a single Python process using OS threads, single node.

### Cited Findings
- Code: `initialize_scheduler` reads `use_context = llms_config.get("use_context_manager", False)` and constructs `rr_scheduler(...)` if true, else `fifo_scheduler(...)`. A commented-out block references a `scheduler_type` key that is not active. — [Code: runtime/launch.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch.py)
- Code: the example config has `scheduler: log_mode: "console"` as the only scheduler setting, and `llms.use_context_manager: false` as the default, so FIFO is the default scheduler. — [Code: config.yaml.example](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/config/config.yaml.example)

- Paper: the "modular design ensures that new scheduling algorithms can be introduced without modifying existing implementations". — [Paper v4, App. A.3](https://arxiv.org/html/2403.16971v4)
- Code: scheduler factories are hard-coded functions (`useFIFOScheduler`, `fifo_scheduler`, `fifo_scheduler_nonblock`, `rr_scheduler_nonblock`) that import `FIFOScheduler` and `RRScheduler` directly; there is no registry, plugin entry point or config-driven class loading. `SchedulerParams` (pydantic) has fields `llm`, `memory_manager`, `storage_manager`, `tool_manager`, `log_mode` and the four queue getters. — [Code: aios/hooks/modules/scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/modules/scheduler.py); [Code: aios/hooks/types/scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/hooks/types/scheduler.py)
- A September 2026 feature request states "There is ... no way to select a scheduling policy" and proposes "A policy registry, so a policy can be selected by name in `config.yaml` (e.g. `fcfs`, `round_robin`, `priority`, `fair_share`) instead of being determined internally". — [Issue #554](https://github.com/agiresearch/AIOS/issues/554)
- Runtime: the README states supported versions are Python 3.10 to 3.11; the kernel is a FastAPI app served by `uvicorn.run(app, host, port)` and started with `python -m runtime.launch`; default `server: host: "localhost", port: 8000`. — [README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md); [Code: runtime/launch.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch.py); [Code: runtime/launch_kernel.sh](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch_kernel.sh)
- Docs: the Syscall class is "Built on Python's threading model". — [Docs: syscalls](https://docs.aios.foundation/aios-docs/aios-kernel/syscalls)
- A user describes the design as "a single-process multiple-threads via a global scheduler" and asks about the Python GIL; no maintainer has answered (one third-party reply argues the workload is I/O-bound). — [Issue #532, opened 2026-03-23](https://github.com/agiresearch/AIOS/issues/532)

### Inferences
- A custom scheduler has a narrow but workable seam: it receives the four manager objects and four blocking `get` callables, and it decides when to call `llm.execute_llm_syscalls(list)` or `manager.address_request(syscall)`. It can reorder, hold back, batch or rate-limit, because it is the only consumer of the queues. It can see `agent_name`, `pid`, `created_time`, the query (messages, tools, requested `llms`) and the unused `priority`.
- What the seam does not give: the getters are destructive pops with a 0.1 s timeout, so a policy that needs to look at the whole backlog must drain into its own structure; there is no admission hook (enqueue happens in `SyscallExecutor` straight onto the global queue), no completion callback other than the syscall's event, no token or cost accounting interface, and no backend load signal.
- Wiring a custom scheduler means editing `runtime/launch.py` and `aios/hooks/modules/scheduler.py` (or replacing the global queue getters). The paper's "without modifying existing implementations" holds for the scheduler classes, not for selection.
- An external (out-of-process, non-Python) scheduler would have to either sit behind a thin Python `BaseScheduler` shim that forwards decisions, or sit in front of the kernel/backends as a proxy. Nothing in the docs or code describes such an integration.
- All queue state is in process memory, so the kernel is single-node and loses queued and suspended work on restart; I found no persistence, replication, leader election or multi-kernel coordination in the scheduler code.

### Gaps
- The contents of the docs' "Scheduler Settings" block did not render, so I cannot say whether the docs show keys beyond `log_mode`.
- I did not find a tutorial or docs page on writing a custom scheduler beyond the `BaseScheduler` method table.

## What performance results do the AIOS papers report for scheduling (throughput, waiting time, turnaround time, vs. no scheduling)? What are the benchmarks and numbers?

### Takeaway
On a single RTX A5000 with one local LLM that serves one prompt at a time, the paper reports up to 2.1x throughput versus running agent frameworks without AIOS, and a ReAct/HumanEval ablation where FIFO and RR roughly halve overall execution time (152.1 s to 74.2 s and 77.3 s) and cut average agent waiting time from 9.8 s to about 3 s. Most efficiency results are normalized bar charts without published absolute values.

### Cited Findings
- Setup: models are GPT-4o-mini (API), Llama-3.1-8b and Mistral-7b (float16); "Ubuntu 22.04 machine equipped with NVIDIA RTX A5000 GPUs (24GB). We run all experiments using a single A5000 GPU". — [Paper v4, §4.1](https://arxiv.org/html/2403.16971v4)
- Workload: "a resource-constrained scenario in which agents run concurrently with a single LLM deployed that can process only one prompt request at a time"; maximum working threads set to 250 by default; "By default, we use RR as the scheduling strategy for AIOS". — [Paper v4, §4.1](https://arxiv.org/html/2403.16971v4)
- Agent frameworks: ReAct, Reflexion, Autogen, Open-Interpreter, MetaGPT. Benchmarks: HumanEval, MINT (code), GAIA, SWE-Bench-Lite. — [Paper v4, §4.1 and Table 1](https://arxiv.org/html/2403.16971v4)
- Metrics: throughput is "the number of AIOS system calls executed per second"; latency is "the average waiting time experienced by agents, from the moment a query is submitted to the completion of the response". Efficiency runs use only the two locally hosted models to avoid API network variance. — [Paper v4, §4.3](https://arxiv.org/html/2403.16971v4)
- Headline: AIOS achieves up "to a 2.1x increase in throughput when using Reflexion-based agents on Llama-3.1-8b". The paper attributes this to scheduling "which prevents unnecessary trial-and-error attempts by avoiding prompts that cannot be loaded onto the GPU for execution". — [Paper v4, §4.3](https://arxiv.org/html/2403.16971v4)
- The baseline failure mode described: existing frameworks "employ an inefficient trial-and-error approach for LLM calls: prompts are converted to tensors and loaded into GPU memory until CUDA memory limits trigger exceptions, forcing tensor deallocation and requiring multiple retry attempts". — [Paper v4, §1](https://arxiv.org/html/2403.16971v4)
- Scheduling-strategy ablation (ReAct agents, HumanEval, Llama-3.1-8b; seconds), Table 6:

  | Strategy | Overall execution time | Avg. agent waiting time | p90 agent waiting time |
  | --- | --- | --- | --- |
  | None (no AIOS) | 152.1 | 9.8 | 11.0 |
  | FIFO | 74.2 | 3.0 | 5.0 |
  | RR | 77.3 | 3.2 | 4.2 |

  — [Paper v4, App. D.1](https://arxiv.org/html/2403.16971v4)
- Paper's reading of Table 6: FIFO has the shortest overall time; RR is second "as its context switching introduces additional overhead" but is better at p90 "due to its fairer scheduling approach". — [Paper v4, App. D.1](https://arxiv.org/html/2403.16971v4)
- Scalability: agents increased from 250 to 2000 on HumanEval (164 samples duplicated to match agent counts) with Llama-3.1-8b and Mistral-7b; "AIOS maintains approximately linear relationships between both overall execution time and average agent waiting time relative to agent count", and the gap versus no-AIOS "widens as agent counts increase". Results are in Figure 8; no table of values. — [Paper v4, §4.4](https://arxiv.org/html/2403.16971v4)
- Throughput and latency for MINT, GAIA and SWE-Bench-Lite are given as normalized figures (Figures 10 to 15). — [Paper v4, App. D.1](https://arxiv.org/html/2403.16971v4)
- The kernel returns per-request `waiting_times` and `turnaround_times` lists in every syscall response, so these metrics are observable from the SDK side. — [Code: aios/syscall/syscall.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/syscall/syscall.py)

### Inferences
- The measured benefit is mostly an admission-control effect against a specific baseline: many agent threads each calling a local HuggingFace model on one 24 GB GPU and retrying on CUDA out-of-memory. Serializing requests removes the retries. The paper's own attribution says this. The result does not show that FIFO or RR beat a baseline that already queues requests, such as a vLLM or Ollama server with its own batching.
- FIFO and RR differ by about 4% in total time and 0.8 s at p90 in the one ablation reported, on one framework, one benchmark and one model. There is no evidence in the paper for heterogeneous request lengths, mixed priorities, multiple models, multiple GPUs or API backends under rate limits.
- "Throughput" counts syscalls per second across all four classes, so it is not tokens per second or tasks per second.
- The paper's FIFO is described as serving a backend that handles one prompt at a time; the current code's FIFO fires each batch concurrently. The published FIFO numbers therefore may not describe today's `FIFOScheduler` behaviour.

### Gaps
- No absolute throughput (syscalls/s) or latency values are published for the main efficiency figures; only normalized charts. Figure 8 values for 250 to 2000 agents are not tabulated.
- The paper does not report turnaround time as a separate metric, nor variance, confidence intervals or number of runs for Table 6.
- I did not read the Cerebrum SDK paper or the LiteCUA, A-MEM and LSFS papers for additional scheduling measurements; none were surfaced by the sources read.
- I found no independent reproduction of the scheduling results.

## What limitations or future work do the docs/paper/issues acknowledge regarding scheduling (e.g. no priority, no resource/GPU awareness, no multi-node, no fairness, rate limits of API backends, batching)?

### Takeaway
The project itself has listed semantic, priority-based, multi-LLM and collaborative scheduling as unimplemented roadmap items since May 2024, and none had landed by November 2026. Issues document no priority or fairness, no policy selection, GIL questions and a broken RR path; rate limits, GPU awareness and multi-node operation are not addressed by the scheduler at all.

### Cited Findings
- Roadmap issue #127 ("AIOS Roadmap Q4 2024", opened 2024-05-16, still open) lists under "AIOS Semantic Scheduling": "Efficiency-based Prompt-level Scheduling", "Priority-based Agent-level Scheduling", "Multi-core AIOS based on Multi-LLM Scheduling", "AIOS Multi-task Collaborative Scheduling". Under "Optimize the LLM kernel": "Translate current implementation to more efficient implementation", "Multi-thread/Multi-process optimization". A December 2025 comment asks "where are the new roadmaps for 2025 adn 2026?" with no maintainer reply. — [Issue #127](https://github.com/agiresearch/AIOS/issues/127)
- Paper future directions, "Semantic Scheduling Algorithms": future work "could focus on algorithms that perform dependency analysis among agent requests, optimizing the allocation of computational resources", and locally deployed tool models "can also be incorporated into the scheduling paradigm ... a unified scheduling framework that encompasses both agents and their tools". — [Paper v4, App. E.2](https://arxiv.org/html/2403.16971v4)
- Paper future directions, context management: "time-efficient context management techniques" to speed up snapshot and restore, and "context compression techniques ... prior to snapshotting". — [Paper v4, App. E.2](https://arxiv.org/html/2403.16971v4)
- Paper acknowledges FIFO "may increase waiting times for later requests" and that RR's "context switching introduces additional overhead". — [Paper v4, §3.3 and App. D.1](https://arxiv.org/html/2403.16971v4)
- Issue #554 (opened 2026-09-13, a student group's feature request): turn order is decided only by FIFO and RR; "There is no way to mark an agent as urgent, no way to guarantee an agent a minimum share of LLM capacity, and no way to select a scheduling policy"; "One long-running agent blocks a short interactive agent completely"; "No shares, no weights, no accounting exist"; "no starvation protection". It proposes priority levels using the existing `priority` field, fair-share weights, aging and a policy registry. — [Issue #554](https://github.com/agiresearch/AIOS/issues/554)
- Issue #532 (2026-03-23) raises the GIL: whether single-process multi-threading sacrifices pipelining "between different system calls ... overlapping some Python executions and LLM decode executions". Unanswered by maintainers. — [Issue #532](https://github.com/agiresearch/AIOS/issues/532)
- Issue #504 / PR #560: RR LLM dispatch raises `TypeError` on `main`; unfixed for over 15 months as of 2026-11-07. — [Issue #504](https://github.com/agiresearch/AIOS/issues/504); [PR #560](https://github.com/agiresearch/AIOS/pull/560)
- In February 2025 a maintainer wrote: "Our current priority is working on the Scheduler, Memory, and Storage modules". — [Issue #438](https://github.com/agiresearch/AIOS/issues/438)
- Rate limits: the LLM adapter maps a backend `RateLimitError` to an `LLMResponse` with status 429 and the message "Rate Limit Exceeded for model ... Please try again later", marked `finished=True`. The scheduler files contain no rate limiter, token bucket, backoff or retry. — [Code: aios/llm_core/adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py); [Code: aios/scheduler/fifo_scheduler.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/fifo_scheduler.py)
- Batching: FIFO "batching" is time-window collection followed by one thread per request; requests are not merged into a single batched inference call. — [Code: aios/llm_core/adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py)
- GPU/resource awareness: the only GPU-related settings are per-model `max_gpu_memory` and `eval_device` for the HuggingFace backend; they configure model loading, not scheduling. — [Code: config.yaml.example](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/config/config.yaml.example); [Docs: configuration](https://docs.aios.foundation/aios-docs/getting-started/environment-variables-configuration)
- Multi-model placement is done by the LLM router, not the scheduler: "Sequential Routing" cycles through the models an agent allows, and "Smart Routing" is "A cost-quality optimized strategy" using "Lagrangian dual optimization". Config default is `router.strategy: "sequential"`. — [Docs: LLM routing](https://docs.aios.foundation/aios-docs/aios-kernel/llm-cores/llm-routing); [Code: config.yaml.example](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/config/config.yaml.example)
- Multi-tenant resource allocation is named only as a future technique: Mode 4 needs "Scheduling and resource allocation mechanism for different virtual machines located in the same machine". — [Docs: index](https://docs.aios.foundation/aios-docs)
- Docs staleness: kernel and scheduler pages show "Last updated 1 year ago". — [Docs: scheduler](https://docs.aios.foundation/aios-docs/aios-kernel/scheduler)

### Inferences
- Limitations not stated by the project but visible in the code: no priority use, no per-agent or per-user fairness or quotas, no deadlines or SLOs, no awareness of token counts or expected generation length, no backend capacity or queue-depth model, no concurrency cap on LLM calls in FIFO, serial handling of tool/memory/storage syscalls, no backpressure (unbounded queues), no persistence, and scheduler parameters that are not configurable.
- Routing (which model) and scheduling (when) are decoupled and uncoordinated: the router's sequential index or cost-quality choice does not consider how busy a backend is, and the scheduler does not know which backend a request will land on until the adapter routes it.
- The roadmap item "Multi-core AIOS based on Multi-LLM Scheduling" is the project's own name for backend-aware placement, and it is still open, which suggests an external scheduler would be filling a gap the maintainers have acknowledged for more than two years.
- Scheduler development velocity appears low: the only scheduler-related activity found in 2026 is community-driven (issues #532, #554, draft PR #560), with no maintainer response on any of the three.

### Gaps
- I found no explicit statement in the docs or paper about API rate limits, GPU-aware scheduling, multi-node kernels or batching as limitations; those points are absent rather than acknowledged. The paper's main text has no dedicated limitations section in the parts I extracted.
- Issue search for "scheduler" returned 37 results; I read #127, #504, #532, #554, #558 and PR #560 plus a few older bug reports. Issues #555 and #557 (September 2026) and GitHub Discussions were not read.
- Whether issue #554's authors have opened a PR is unknown.

## How does AIOS deploy (local kernel server, remote kernel, modes described in docs), and how do LLM backends (OpenAI API, ollama, vLLM, HF local) affect what a scheduler can control?

### Takeaway
AIOS deploys as one kernel HTTP server (default `localhost:8000`) that agents reach through the Cerebrum SDK either on the same machine (Mode 1) or remotely (Mode 2); Modes 2.5, 3 and 4 are described but not shipped. Only the in-process HuggingFace backend gives the kernel real control over generation; for cloud APIs, Ollama and vLLM the scheduler controls only when and how many HTTP requests are sent, and the remote server does its own queuing and batching.

### Cited Findings

#### Deployment
- Docs define four machine roles: Agent Hub Machine (AHM), Agent UI Machine (AUM), Agent Development Machine (ADM), Agent Running Machine (ARM). — [Docs: index](https://docs.aios.foundation/aios-docs)
- Mode 1 (Local Kernel): agents and kernel on the same machine, agent hub elsewhere. Mode 2 (Remote Kernel): users use agents from a different machine than the one running them, for "resource-restricted machine (e.g., mobile device or edge device)". Mode 2.5 (Remote Kernel Dev): develop on one machine, run and test on another. Mode 3 (Personal Remote Kernel): per-user persistent AIOS with account registration and sync. Mode 4 (Personal Remote Virtual Kernel): multiple users' kernels virtualized on one physical machine. — [Docs: index](https://docs.aios.foundation/aios-docs)
- README: "Currently, AIOS already supports Mode 1 and Mode 2, other modes with new features are still ongoing." — [README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)
- README: for Remote Kernel mode, install kernel and SDK on Machine 1 and the SDK alone on Machine 2; "the agents remotely interact with the kernel". — [README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)
- Kernel/SDK split dates from v0.2 (2024-11-30): "Disentangled AIOS Kernel ... and AIOS SDK (The Cerebrum repository), Remote Kernel for agent users". v0.2.2 followed a "major refactor" (2025-03-12). — [README news](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)
- Latest release is v0.3.0 (released 22 January; the page does not show the year, but it includes a fix for an issue opened in November 2025, so January 2026). Its changelog includes the Rust scaffold (#505), Qdrant support, a computer-use MCP environment, Novita backend and LLM routing refactor; no scheduler feature is listed. — [Releases](https://github.com/agiresearch/AIOS/releases)
- Kernel HTTP surface in code: `/status`, `/core/status`, `/core/refresh`, `/core/cleanup`, `/core/config/update`, `/core/llms/check`, `/core/llms/list`, `/user/select/llms`, `/agents/submit`, `/agents/ps`, `/agents/{execution_id}/status`, `/query`. `/core/cleanup` stops the scheduler. — [Code: runtime/launch.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/runtime/launch.py)
- The README describes a computer-use variant in which the Tool Manager is "redesigned to incorporate a VM (Virtual Machine) Controller and MCP Server"; the repo contains VM providers for Docker, VMware, VirtualBox, AWS, GCP and Azure under `aios/tool/virtual_env/`. — [README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)
- AIOS "supports both Web UI and Terminal UI". — [Docs: index](https://docs.aios.foundation/aios-docs)

#### Backends
- Docs: three backend categories: "LiteLLM compatible backends (cloud and local)", "vLLM backends (local)" using an OpenAI client, and "Huggingface backends (local)" using the model's generate method. — [Docs: LLM cores](https://docs.aios.foundation/aios-docs/aios-kernel/llm-cores)

- README provider table: Anthropic, OpenAI, Deepseek, Google (Gemini), Groq, HuggingFace, Ollama, vLLM, Novita. The repo also ships `scripts/launch_vllm.sh` and `scripts/launch_sglang.sh`. — [README](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/README.md)

- Code: LiteLLM-style backends are called via `litellm.completion(...)`; vLLM-style backends via an `OpenAI(base_url=config.hostname)` client; HuggingFace via an in-process `HfLocalBackend.generate`. — [Code: aios/llm_core/adapter.py](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/llm_core/adapter.py)
- Context-switch capability by backend: text-based for API models and OpenAI clients; logits-based "Currently only supported for HuggingFace models". — [Docs: context](https://docs.aios.foundation/aios-docs/aios-kernel/context)
- Agents can name one or several acceptable LLMs per request; with several, the kernel's router picks. - The paper's efficiency experiments assume "a single LLM deployed that can process only one prompt request at a time" on a local GPU. — [Paper v4, §4.1](https://arxiv.org/html/2403.16971v4)

### Inferences
- Control by backend type:
  - **HuggingFace in-process**: the kernel owns the GPU and the decode loop, so it can serialize, time-slice with KV-cache snapshots and avoid OOM. This is the configuration the paper's gains were measured on.
  - **vLLM / SGLang / Ollama (local servers)**: the server has its own request queue and (for vLLM/SGLang) continuous batching. The AIOS scheduler can only decide request release order and concurrency. Text-based "preemption" means abandoning a stream and later issuing a new request, which works against the server's batching and cache rather than with it.
  - **Cloud APIs (OpenAI, Anthropic, Gemini, Groq, Deepseek, Novita)**: the binding constraints are provider rate limits (requests and tokens per minute), latency and cost. The scheduler has no model of any of them; a 429 is returned to the agent as a finished error.
- In Mode 2 the scheduler sees remote agents only as HTTP `/query` calls carrying an `agent_name`; it has no knowledge of the client machine, and every syscall adds a network round trip. Agents submitted via `/agents/submit` run inside the kernel process and share its GIL and thread pool.
- All modes that exist today have one kernel process per deployment. Modes 3 and 4, which would require per-user isolation and cross-kernel resource allocation, are where a cluster-level or multi-tenant scheduler would matter, and they are unimplemented.
- Since default config points at Ollama and the default scheduler is FIFO with unbounded per-batch concurrency, a default AIOS install effectively delegates LLM scheduling to the Ollama server.

### Gaps
- I did not verify how Ollama is invoked in detail (it appears to go through the LiteLLM path with `api_base`), nor whether the Dockerfile in the repo represents a supported deployment mode; docs do not describe a container or Kubernetes deployment.
- No documentation was found on authentication, multi-user isolation or TLS for the remote kernel endpoint.
- I did not confirm whether the AIOS Foundation operates a hosted kernel, or the current state of the agent hub service.
- The individual backend sub-pages of the docs (LiteLLM, vLLM, HuggingFace) were not fetched; backend facts come from the parent page, config and adapter code.
