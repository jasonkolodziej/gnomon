# Evidence: does sophisticated (HPC/cluster-style) scheduling improve LLM-agent and LLM-inference systems vs. AIOS-style FIFO/RR?

Research date: 2026-11-20. Provenance legend used below:
- **[full text]** = number read in the paper body/table.
- **[abstract]** = number taken from the paper's own abstract (author-reported headline, usually "up to").
- **[search summary]** = number seen only in a search-result summary, not verified against the page; treat as lower confidence.
- All paper numbers are author-reported measurements on their own testbeds; none is an independent replication.

## 1. What do published works report about scheduling for LLM agents and LLM serving?

### Takeaway
Every published system that beats FIFO/FCFS for LLM or agent workloads does so with *LLM-specific* signals (attained service per program, output-length rank, token counts, KV-cache/prefix locality, workflow DAG) applied *inside or directly in front of the inference engine's batch loop*; reported gains are large (1.5x to 15x throughput, 14-79% JCT, 8x JCT) but none uses HPC batch mechanisms (walltime-based backfill, node allocation, resource-graph matching). AIOS's own ablation shows its scheduler choice barely matters in its test setup (FIFO 74.2 s vs RR 77.3 s), and its headline 2.1x comes from serialising access to a single-request LLM, not from the policy.

### Cited Findings

**AIOS baseline (arXiv 2403.16971v4)**
- AIOS implements two syscall scheduling algorithms, FIFO and Round Robin; RR is enabled by a "context interrupt" mechanism (logits-based context snapshot/restore) that enforces a time limit on generation. The scheduler "centralizes queue management across all modules"; syscalls are routed to per-module queues (LLM, memory, storage, tool). [full text] — [AIOS paper](https://arxiv.org/html/2403.16971v4)
- Test setup: one Ubuntu 22.04 machine, a **single NVIDIA RTX A5000 (24 GB)**; Llama-3.1-8b and Mistral-7b (float16) locally, GPT-4o-mini via API; "agents run concurrently with a single LLM deployed that can **process only one prompt request at a time**"; 250 worker threads by default; RR is the default policy. [full text] — [AIOS paper](https://arxiv.org/html/2403.16971v4)
- Scheduling-strategy ablation (ReAct agents, HumanEval, Llama-3.1-8b; seconds): **None (no AIOS): 152.1 overall, 9.8 avg wait, 11.0 p90 wait; FIFO: 74.2 / 3.0 / 5.0; RR: 77.3 / 3.2 / 4.2.** The authors say FIFO is fastest overall, RR is slower because "context switching introduces additional overhead", and RR wins only on p90 wait. [full text, Table 6] — [AIOS paper](https://arxiv.org/html/2403.16971v4)
- Headline: "up to 2.1x faster execution"; the 2.1x throughput figure is for Reflexion agents on Llama-3.1-8b. Throughput is defined as AIOS syscalls executed per second; latency as average agent waiting time. The authors attribute the gain to scheduling "which prevents unnecessary trial-and-error attempts by avoiding prompts that cannot be loaded onto the GPU for execution". [full text] — [AIOS paper](https://arxiv.org/html/2403.16971v4)
- Scalability: 250 to 2000 agents on HumanEval (164 samples duplicated); overall execution time and average waiting time grow "approximately linear" with agent count. [full text] — [AIOS paper](https://arxiv.org/html/2403.16971v4)
- The appendix states the `BaseScheduler` class is meant to be subclassed for "FIFO, Round Robin, and priority-based scheduling", i.e. the extension point exists but no priority results are reported. [full text] — [AIOS paper](https://arxiv.org/html/2403.16971v4)

**Program-/workflow-level agent scheduling**
- **Autellix** (arXiv 2502.13965): treats an agent "program" (dynamic DAG of LLM calls) as the scheduling unit. Two non-clairvoyant policies: PLAS (Program-Level Attained Service, single-threaded) and ATLAS (critical-path attained service, multi-threaded), discretised into K MLFQ-style queues with a wait/service-ratio anti-starvation rule. Implemented as a modified scheduler inside vLLM v0.6.1 plus a locality-aware load balancer. Testbed: GCP a2-ultragpu-8g, 8x A100-80GB; LLaMA-3.1-8B/70B, Falcon-180B; workloads ShareGPT, BFCL, LATS, mixed. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- Autellix results: 4-15x program throughput at equal latency vs vLLM [abstract]. Breakdown [full text]: single-threaded (ShareGPT, BFCL) up to 8x vs vLLM, 2x vs vLLM-opt (vLLM + prefix caching), 1.5x vs MLFQ; multi-threaded LATS up to 5x / 2x / 2.5x vs vLLM / vLLM-opt / MLFQ; mixed workload up to 15x / 4x / 5.5x. Tail: lower P95/P99 than MLFQ and vLLM-opt in 7 of 8 scenarios, up to 1.7x throughput at P95/99 targets. Offline batch: makespan reduced 10-40%. — [Autellix](https://arxiv.org/html/2502.13965v1)
- Autellix on plain preemption: call-level MLFQ (the FastServe approach) only gives 1.5x over vLLM on single-threaded work and "may perform close to, or even worse, than FCFS" because of program-level head-of-line blocking; at 4000 programs MLFQ **OOMs** despite >1.2 TB swap space because preemption multiplies live KV caches. Preemptive policies have higher scheduling time than FCFS. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- Autellix locality: within one program KV cache-hit rate stays above 90% across input lengths; across programs it decays exponentially (only the system prompt is shared). Locality-aware routing gives up to 1.4x throughput vs round-robin and least-used balancers over 4 replicas ("up to 1.5x" in the intro). [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- Autellix simulation: it beats FCFS, RR and MLFQ but "a noticeable gap remains between Autellix and SRPT, showing that prior knowledge can significantly boost performance". [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- **Parrot** (OSDI'24): exposes application-level dataflow ("Semantic Variables") to the LLM service so it can optimise across correlated requests; "up to an order-of-magnitude improvement" for popular LLM applications. [abstract] — [Parrot](https://arxiv.org/abs/2405.19888)
- **Teola** (ASPLOS'25; the task brief calls it Ayo/Teola): primitive-level dataflow graph across LLM and non-LLM components, enabling parallelisation/pipelining; up to 2.09x speedup over existing orchestration frameworks. [abstract] — [Teola](https://arxiv.org/abs/2407.00326)
- **LLMSched** (ICDCS'25): DAG model with Bayesian-network profiling of duration/structure uncertainty for compound LLM apps; average JCT reduced 14-79% vs "state-of-the-art scheduling schemes" in simulation and testbed. [abstract] — [LLMSched](https://arxiv.org/abs/2504.03444)
- **Kairos**: workflow-aware priority scheduler plus memory-aware dispatcher for multi-agent apps sharing one LLM; end-to-end latency down 17.8-28.4% vs state of the art. [abstract] — [Kairos](https://arxiv.org/abs/2508.06948)
- **Continuum**: pins an agent's KV cache in GPU memory with a TTL across tool calls, combined with program-level FCFS; average JCT improved "over 8x" with higher throughput on SWE-Bench, BFCL, OpenHands with Llama-3.1 8B/70B, Gemma-3 12B, GLM-4.5. [abstract] — [Continuum](https://arxiv.org/abs/2511.02230)
- **KVFlow**: workflow-aware KV eviction and prefetch using an Agent Step Graph; up to 1.83x (single workflow, large prompts) and 2.19x (many concurrent workflows) over SGLang's hierarchical radix cache. [abstract] — [KVFlow](https://arxiv.org/abs/2507.07400)
- **Maestro** (2026): hierarchical node/cluster/global scheduler for multi-agent serving that predicts per-stage output length and memory; reduces KV-reservation memory by 67.2% and improves high-contention SLO attainment by 23.6 percentage points over EDF (prototype plus trace-driven simulation). [abstract] — [Maestro](https://arxiv.org/abs/2606.12950). Preempts background stages only at stage boundaries (between LLM invocations) with hysteresis. [search summary] — [Maestro](https://arxiv.org/pdf/2606.12950)
- **AgentRM** (March 2026): middleware "OS-inspired" resource manager built from an analysis of 40,000+ GitHub issues across six agent frameworks; identifies blocking, zombie processes and **rate-limit cascades** as the scheduling failures. Its MLFQ scheduler with zombie reaping and rate-limit-aware admission control reports P95 latency -86%, lane waste -96%, throughput +168%, zombies 0 vs 29 baseline. [abstract] — [AgentRM](https://arxiv.org/abs/2603.13110)

**Request-level LLM serving schedulers**
- **vLLM / PagedAttention** (SOSP'23): 2-4x throughput at the same latency vs FasterTransformer and Orca via paged KV-cache memory enabling larger batches; default policy is FCFS. [abstract; FCFS default per Autellix full text] — [vLLM](https://arxiv.org/abs/2309.06180), [Autellix](https://arxiv.org/html/2502.13965v1)
- **FastServe**: token-granularity preemption with a skip-join MLFQ and proactive KV offload to host memory; up to 31.4x / 17.9x throughput vs vLLM under the same average / tail latency requirement. [abstract] — [FastServe](https://arxiv.org/abs/2305.05920)
- **Learning to Rank** (approximate SJF): predicts relative rank of output lengths rather than exact length; 2.8x lower latency in chatbot serving and 6.5x higher throughput in synthetic data generation, integrated into a state-of-the-art serving system. [abstract] — [Efficient LLM Scheduling by Learning to Rank](https://arxiv.org/abs/2408.15792)
- **TRAIL**: predicts remaining length from the LLM's own embeddings; SRPT variant with *limited* preemption because preemption costs memory for retained state. No headline number in the abstract. [abstract] — [TRAIL](https://arxiv.org/abs/2410.01035)
- **S3**: output-length prediction for batch packing; 6.49x throughput over systems that reserve worst-case sequence length. [abstract] — [S3](https://arxiv.org/abs/2306.06000)
- **VTC, "Fairness in Serving LLMs"** (OSDI'24): token-weighted fair scheduler on continuous batching; proves a tight 2x upper bound on the service difference between two backlogged clients while staying work-conserving; argues RPM rate limits under-utilise spare capacity. Reports fairness, not a throughput gain. [abstract] — [VTC](https://arxiv.org/abs/2401.00588)
- **DLPM / D2LPM**: locality-aware fair scheduling; up to 2.87x higher throughput than VTC and up to 7.18x lower per-client latency than a state-of-the-art distributed serving system, because VTC ignores prefix locality. [abstract] — [Locality-aware Fair Scheduling](https://arxiv.org/abs/2501.14312)
- **Llumnix** (OSDI'24): live migration of requests and their in-memory state across model instances; tail latency improved by an order of magnitude, high-priority requests up to 1.5x faster, up to 36% cost saving at similar tail latency. [abstract] — [Llumnix](https://arxiv.org/abs/2406.03243)
- **Andes**: token-level preemptive scheduling for streaming QoE; up to 4.7x average QoE at equal GPU, or up to 61% GPU saving at equal QoE. [abstract] — [Andes](https://arxiv.org/abs/2404.16283)
- **QLM**: queue management across batch and interactive requests, models and SLOs with a waiting-time estimator; SLO attainment +40-90%, throughput +20-400%. [abstract] — [QLM](https://arxiv.org/abs/2407.00047)

### Inferences
- The AIOS ablation is not evidence that scheduling is unimportant; it is evidence that with one LLM serving one prompt at a time and a homogeneous workload (164 HumanEval items duplicated), policy has almost nothing to act on. The "None" to FIFO gap (152.1 s to 74.2 s) measures the value of having *any* admission queue, which a sophisticated scheduler would also provide but cannot improve on much.
- The gains that matter (Autellix 4-15x, Continuum 8x, FastServe, LTR) require the scheduler to (a) see the engine's running batch and KV-cache state and (b) know which calls belong to the same agent program. A scheduler that only orders requests before they reach an engine doing continuous batching can capture the program-level ordering part (PLAS-style priority, fair-share, quotas) but not the preemption/KV-management part.
- HPC-scheduler features map unevenly onto this literature: **priority** and **fair-share** have direct analogues with measured value (PLAS/ATLAS, VTC, DLPM, Kairos, QLM); **preemption** has value but only with engine cooperation and memory-aware limits (FastServe, TRAIL, Autellix's MLFQ OOM); **backfill** has no published analogue for LLM syscalls because it needs runtime estimates; **resource-graph matching** has an analogue only as locality/memory-aware routing across replicas (Autellix balancer, Llumnix, Kairos dispatcher, Maestro), i.e. multi-engine deployments, which AIOS's evaluation does not exercise.
- AgentRM's result suggests a second high-value niche independent of GPU scheduling: rate-limit-aware admission control and liveness (zombie reaping) for API-backed agents.

### Gaps
- Could not fetch docs.aios.foundation, so there are no numbers beyond the paper for the current AIOS scheduler (e.g. whether newer releases add priority or batching). The paper only reports FIFO and RR.
- Parrot's per-application numbers and baselines (only "up to an order of magnitude" was read), VTC's quantitative fairness tables, and Llumnix/LTR full-text baselines were not read beyond abstracts.
- vLLM's and TGI's current built-in policies (e.g. priority scheduling options, continuous-batching parameters) were not verified from project docs; "FCFS default" is as reported by the Autellix and LTR papers for the versions they used.
- No paper was found that evaluates a priority/backfill/fair-share scheduler head-to-head against AIOS's FIFO/RR inside AIOS itself.
- "Ayo" as the name of Teola's code release is from the task brief; it was not verified.

## 2. Where is the bottleneck in agent systems, and what does that imply for where a scheduler adds value?

### Takeaway
There is no single bottleneck: under load on a self-hosted GPU the dominant term is queueing in front of / inside the engine (which scheduling can cut), but tool execution and sandbox start-up account for a comparable or larger share in many agent workloads (55-60% in one coding-agent study, up to ~90% in a CPU-centric study), and for API-backed agents the binding constraint is provider rate limits. A scheduler therefore adds value at the engine queue, at tool/sandbox resource admission, and at rate-limit admission, and adds essentially none to LLM execution time itself.

### Cited Findings
- Autellix decomposes a program's end-to-end latency into (1) waiting time in the engine queue, (2) LLM execution time, (3) "interceptions" (tool calls, human input), and states that across chatbot, ReAct and MCTS workloads "the majority of a program's time is spent waiting as load increases"; it explicitly treats (3) as outside LLM serving. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- AgentCgroup (144 SWE-rebench coding tasks, two models): OS-level execution (tool calls plus container and agent initialisation) is 55-60% of end-to-end task latency; **memory, not CPU, is the concurrency bottleneck**; memory spikes are tool-call-driven with up to 15.4x peak-to-average ratio; demands are "highly unpredictable across tasks, runs, and models". [abstract] — [AgentCgroup](https://arxiv.org/abs/2602.09345). Breakdown reported as LLM reasoning 40-45%, tool execution 13-24%, initialisation 31-48%. [search summary] — [AgentCgroup](https://arxiv.org/pdf/2602.09345)
- CPU-centric characterisation: tool processing on CPUs can take up to 90.6% (v2) / 88% (v3) of total latency; throughput is limited either by CPU factors (core oversubscription, synchronisation) or GPU memory. [search summary] — [Raj et al.](https://arxiv.org/abs/2511.00739). Its scheduling fixes give up to 1.7x lower P50 latency standalone, up to 3.9x/1.8x lower service/total latency under open-loop load (COMB), and up to 2.37x/2.49x lower P50/P90 total latency for minority request types (MAS). [abstract] — [Raj et al.](https://arxiv.org/abs/2511.00739)
- "Not All AI Agents Are Equal" (remote LLM APIs plus local tool containers; RAG QA, web search, coding): concurrency exposes task-dependent CPU, disk-I/O and memory bottlenecks; "faster LLM responses or more CPU cores do not always accelerate agents"; CPU-aware tool admission and task-aware CPU allocation improve CPU-sensitive task latency ~5.4x and average latency ~32% vs native agents. [abstract] — [Not All AI Agents Are Equal](https://arxiv.org/abs/2609.19947)
- "Agentic AI Workload Characteristics": with effective context caching most input tokens are reused across turns, making execution **decode-dominated** and increasingly dependent on long-lived KV-cache state; tool use shifts from read/explore early to execute/write late. [abstract] — [Yuan et al.](https://arxiv.org/abs/2605.26297)
- Continuum: engines evict a finished request's KV cache when others are waiting, which "breaks for agentic workloads" that pause for tools; retaining the cache with a TTL is the source of its >8x JCT gain. [abstract] — [Continuum](https://arxiv.org/abs/2511.02230)
- AsyncLM: making function calls asynchronous (not blocking inference) cuts end-to-end task completion latency 1.6x-5.4x on BFCL tasks, i.e. tool wait/serialisation is a first-order term. [abstract] — [AsyncLM](https://arxiv.org/abs/2412.07017)
- Teola: LLM applications contain LLM and non-LLM components "each contributing to the end-to-end latency"; module-level orchestration leaves cross-module parallelism unused (up to 2.09x). [abstract] — [Teola](https://arxiv.org/abs/2407.00326)
- AgentRM: from 40,000+ GitHub issues in six agent frameworks, the scheduling failures users actually hit are blocking, zombie processes and rate-limit cascades. [abstract] — [AgentRM](https://arxiv.org/abs/2603.13110)
- VTC: major inference services use request rate limits for fairness, which wastes spare capacity. [abstract] — [VTC](https://arxiv.org/abs/2401.00588)
- "The Cost of Dynamic Reasoning": agents show rapidly diminishing accuracy returns with more compute and "widening latency variance". [abstract] — [Kim et al.](https://arxiv.org/abs/2506.04301)

### Inferences
- For AIOS specifically there are three distinct schedulable resources with different best-fit mechanisms: (a) the LLM core queue, where program-level priority, fair-share and KV-affinity matter; (b) tool/sandbox execution, which looks like a classic heterogeneous resource-allocation problem (CPU cores, memory, containers) and is where a resource-graph scheduler with quotas and preemption is most natural; (c) remote-API token budgets, a rate-limiting/admission problem.
- An HPC-style scheduler's native strengths (multi-resource matching, reservations, quotas, accounting) align best with (b) and with coarse-grained placement (which agent/job runs on which engine or node), not with per-token decisions in (a).
- Because tool resource demand is bursty (15.4x peak-to-average) and unpredictable, static per-job requests in the batch-scheduler style would either over-reserve or under-protect; the cited fixes operate at tool-call granularity with in-kernel enforcement.
- If the deployment calls a hosted API, the engine queue is not controllable at all; the only scheduler value is admission control against rate limits, fairness between agents, and tool-side resource management.

### Gaps
- No source gives a measured latency breakdown for AIOS itself (LLM queue vs LLM execution vs tools).
- The 90.6%/88% tool-share and the AgentCgroup percentage breakdown come from search summaries; the versions disagree slightly (90.6% vs 88%) and should be checked against the PDFs before being quoted.
- No quantitative public data found on how often provider rate limits (RPM/TPM) are the binding constraint in production agent systems.

## 3. How do existing cluster schedulers handle AI/agent workloads, and is there precedent for an HPC batch scheduler under an agent framework?

### Takeaway
No published system was found that places an HPC batch scheduler (Slurm, Flux or similar) in the per-LLM-call path of an agent framework. The consistent precedent is two-level: the batch scheduler allocates nodes or long-lived engines at coarse granularity, and a lightweight task layer (pilot, Flux sub-instance, HyperQueue, Ray, the inference engine's own queue) handles fine-grained dispatch, because per-job latency of batch schedulers is seconds while task layers reach milliseconds.

### Cited Findings
- Benchmark of Slurm, Son of Grid Engine, Mesos and YARN: for all four, system utilisation drops below 10% for computations lasting only a few seconds; multilevel scheduling that aggregates short tasks restores utilisation above 90%. [abstract] — [Reuther et al., Scalable System Scheduling for HPC and Big Data](https://arxiv.org/abs/1705.03102). Slurm's measured marginal latency was 2.2 s per task (YARN 33 s). [search summary] — [same paper](https://arxiv.org/pdf/1705.03102)
- Slurm defaults: main scheduling loop `sched_interval` 60 s; backfill `bf_interval` 30 s; submissions do not trigger an immediate scheduling pass (governed by `sched_min_interval`; the HTC guide's example batches 100 submissions in 2 s into one pass); for short jobs the guide recommends `sched/builtin` (plain FIFO) to skip priority sorting, and suggests `bf_max_job_test` of about 100 and `bf_interval` of 30 s or more to bound backfill overhead. [search summary of official docs] — [Slurm High Throughput Computing Guide](https://slurm.schedmd.com/high_throughput.html), [Slurm Scheduling Configuration Guide](https://slurm.schedmd.com/sched_config.html)
- RADICAL-Pilot on Frontier (2025): Slurm `srun` peaks at 152 tasks/s, degrades with scale, utilisation below 50%; RP+Flux sustains up to 930 tasks/s; RP+Flux+Dragon exceeds 1,500 tasks/s with over 99.6% utilisation; for a drug-discovery campaign mixing simulation, training and inference, RP+Flux cuts makespan 30-60% vs srun/Slurm. The paper states srun "constrain[s] concurrency and throughput, making [it] unsuitable for dynamic and heterogeneous workloads". [abstract] — [Integrating and Characterizing HPC Task Runtime Systems](https://arxiv.org/abs/2509.20819)
- Flux's hierarchical (nested-instance) scheduling is reported to give up to 48x job-throughput improvement for some ensemble workflows. [search summary] — [Flux FGCS 2020](https://flux-framework.github.io/publications/Flux-FGCS-2020.pdf)
- HyperQueue alongside Slurm for UQ workloads with unpredictable runtimes: scheduling overhead reduced by up to three orders of magnitude and up to 38% CPU-time reduction vs naive Slurm, without assumptions on submission patterns. [abstract] — [UQ workflow scheduling](https://arxiv.org/abs/2503.22645). After a single Slurm allocation, launch overhead falls to the order of milliseconds. [search summary] — [same paper](https://arxiv.org/pdf/2503.22645)
- Kubernetes side: Kueue admission overhead under 25 ms at P99 and up to 15% makespan reduction from priority and preemption on AI inference/transcription batch jobs (vendor research, Red Hat). [search summary] — [Red Hat Research](https://research.redhat.com/blog/article/kubernetes-meets-genai-evaluating-performance-for-ai-inference-workloads/)
- Kubernetes scheduler throughput, project self-benchmarks: default kube-scheduler about 50.5 pods/s vs YuniKorn up to 833.3 pods/s in KWOK simulation; older Kubemark test 617 vs 263 pods/s at 2,000 nodes and 373 vs 141 at 4,000 nodes. [search summary; vendor/project claim] — [YuniKorn KWOK](https://yunikorn.apache.org/docs/performance/evaluate_perf_function_with_kwok), [YuniKorn Kubemark](https://yunikorn.apache.org/docs/performance/evaluate_perf_function_with_kubemark)
- Simulation (5,000-node model, 2026): a Ray-like decentralised scheduler holds P99 near 1.81-2.49 ms up to load 0.7, while a Slurm-like centralised model sits at about 12 s P99. [search summary; simulation, not a measurement of real Ray or Slurm] — [Laminar](https://arxiv.org/pdf/2602.13789)
- Ray: task scheduling is decentralised, while actor creation can be bounded by the central GCS server. [search summary; forum statement] — [Ray forum](https://discuss.ray.io/t/performance-overhead-numbers/4208)
- Agents *driving* HPC schedulers (the reverse relationship): agents translate job specs between Slurm and Flux with high accuracy but monitor jobs inefficiently, preferring fixed waits over event subscriptions. [search summary] — [Descriptive Execution of HPC Applications and Workflows](https://arxiv.org/abs/2607.10081). LLMs used *as* the HPC scheduler (ReAct, 10-100 jobs vs FCFS/SJF/OR-Tools) have noted computational-efficiency limits. [search summary] — [arXiv 2506.02025](https://arxiv.org/abs/2506.02025)
- Autellix notes round-robin is the default Kubernetes load-balancing policy and that it ignores KV-cache locality, costing up to 1.4x throughput in a 4-replica setup. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)

### Inferences
- The decisive number for "batch scheduler under an agent OS" is scheduling latency per unit of work. An LLM syscall is typically hundreds of milliseconds to tens of seconds; a design with Slurm-like periodic passes (seconds) would put the syscall in the regime where the 2017 benchmark saw utilisation below 10%. A new scheduler avoids this only if it is event-driven with sub-millisecond to low-millisecond decision time; the mechanisms (backfill, graph match) are not the problem, the control-loop cadence is.
- Throughput ceilings of real systems give a calibration target: around 150 tasks/s (srun), 930 tasks/s (Flux under RP), 1,500 tasks/s (with Dragon), about 50 to 830 pods/s (Kubernetes schedulers). AIOS at 250-2000 concurrent agents on one GPU generates far fewer syscalls per second than these ceilings, so raw throughput is unlikely to be the limiting factor; added per-call latency is.
- The pattern that worked everywhere (pilot/nested instance) implies the sound integration is hierarchical: the external scheduler grants leases (engine replicas, GPU shares, tool-sandbox slots, token budgets per agent/tenant) and an in-process dispatcher makes per-syscall decisions within the lease.
- Kueue's under-25 ms admission figure shows a queueing/quota layer can be cheap when it only admits jobs and leaves placement to another component; this is the closest precedent for a low-overhead external "admission plus fairness" service.

### Gaps
- No documented deployment or paper was found of Slurm, Flux, Volcano, YuniKorn or Kueue scheduling individual LLM calls or agent syscalls. Absence of evidence after roughly 15 searches/fetches, not proof of absence.
- No verified primary numbers for Ray task throughput/latency or Ray Serve LLM routing overhead; Volcano's and the KubeCon EU 2025 Kueue/Volcano/YuniKorn comparison numbers were not retrieved.
- Slurm parameter values are from a search summary of the official docs (versions up to 24.11); confirm against the current slurm.conf man page.
- The Flux "48x" claim and the Slurm 2.2 s marginal latency are from search summaries of the cited PDFs.

## 4. Known mismatches between batch-job scheduling and LLM syscall scheduling

### Takeaway
Batch scheduling assumes declared resource and runtime bounds, independent jobs and expensive but rare preemption; LLM syscalls have unknown output length, strong inter-call dependence and cache state, token-level preemption with memory cost, and resource demand that changes within a job. The literature's answer is non-clairvoyant or rank-based policies with KV-aware limits on preemption, not estimate-driven backfill.

### Cited Findings
- **Unknown runtime.** Output length "is typically regarded as not known a priori", which is why serving systems default to FCFS; exact length prediction is infeasible but relative *rank* within a batch is predictable. [abstract] — [Learning to Rank](https://arxiv.org/abs/2408.15792). Accurate length prediction from prompts is "challenging and often resource-intensive". [abstract] — [TRAIL](https://arxiv.org/abs/2410.01035)
- **Value of runtime knowledge.** Autellix assumes "no prior workload knowledge" (non-clairvoyant) yet reports a noticeable gap to SRPT in simulation. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1). LLMSched models "duration and structural uncertainty" of compound apps with a Bayesian network and schedules uncertainty-reducing stages first (14-79% JCT). [abstract] — [LLMSched](https://arxiv.org/abs/2504.03444)
- **Job structure is unknown and dynamic.** Agent programs are "dynamic, non-deterministic DAGs of LLM calls and interrupts"; the DAG is built at runtime. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- **Preemption granularity and cost.** Preemption is possible per output token (FastServe, Andes) but each preempted request keeps KV state; TRAIL restricts preemption late in a request for this reason; Autellix discretises priorities into queues to avoid "frequent KV-cache swaps between CPU and GPU"; call-level MLFQ ran out of memory at 4000 programs. — [FastServe](https://arxiv.org/abs/2305.05920), [Andes](https://arxiv.org/abs/2404.16283), [TRAIL](https://arxiv.org/abs/2410.01035), [Autellix](https://arxiv.org/html/2502.13965v1)
- **AIOS's preemption form.** Time-limit-based interruption of a streaming generation with snapshot and restore of the intermediate state; in the ablation it made RR slower overall than FIFO (77.3 s vs 74.2 s) while improving p90 wait (4.2 s vs 5.0 s). [full text] — [AIOS](https://arxiv.org/html/2403.16971v4)
- **Cache affinity as a placement constraint.** Within-program KV hit rate above 90%; cross-program hit rate decays exponentially with input length. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1). VTC-style fairness without prefix locality loses up to 2.87x throughput. [abstract] — [DLPM](https://arxiv.org/abs/2501.14312). Agent workloads are decode-dominated with dependence on long-lived KV state. [abstract] — [Yuan et al.](https://arxiv.org/abs/2605.26297)
- **Resources are held across idle gaps.** Tool calls create pauses in which an agent's KV cache must be either pinned (occupying GPU memory while idle) or evicted and recomputed; Continuum sets a TTL from reload cost vs queueing delay. [abstract] — [Continuum](https://arxiv.org/abs/2511.02230)
- **Batching instead of exclusive allocation.** LLM engines serve many requests concurrently; throughput depends on batch size, limited by KV memory. [abstract] — [vLLM](https://arxiv.org/abs/2309.06180). Fairness must be defined on input and output tokens under continuous batching, not on request counts or time slices. [abstract] — [VTC](https://arxiv.org/abs/2401.00588)
- **Objective mismatch.** Request-level metrics (TTFT, TPOT) "overlook end-to-end latency for agentic programs". [full text] — [Autellix](https://arxiv.org/html/2502.13965v1). Streaming QoE depends on first-token time and token delivery pace. [abstract] — [Andes](https://arxiv.org/abs/2404.16283)
- **Resource-control mismatches named explicitly for agents** (vs serverless, microservice and batch workloads): granularity (container-level policy vs tool-call-level dynamics), responsiveness (user-space reaction vs sub-second bursts), adaptability (history-based prediction vs non-deterministic stateful execution). [abstract] — [AgentCgroup](https://arxiv.org/abs/2602.09345)
- **Time-scale mismatch.** Batch schedulers lose over 90% utilisation on few-second tasks unless tasks are aggregated. [abstract] — [Reuther et al.](https://arxiv.org/abs/1705.03102)
- **Batch-scheduler assumptions already fail for dynamic HPC workloads.** "A static one-size-fits-all batch script would likely lead to suboptimal scheduling" for tasks with unpredictable runtimes and unknown total count. [abstract] — [UQ workflows](https://arxiv.org/abs/2503.22645)

### Inferences
- Conservative/EASY backfill depends on walltime estimates to guarantee the head job's reservation is not delayed. With no usable estimate per LLM call, backfill degenerates; the workable substitutes are (i) `max_tokens` as a hard upper bound (a "walltime limit" that is usually very loose), (ii) rank or attained-service ordering. Backfill is plausible only at coarser granularity where bounds exist, e.g. packing whole agent tasks or tool jobs with declared CPU/memory/time limits into reserved windows.
- A resource graph can model engines, GPU memory and KV-cache residency, but KV residency is soft state that changes every few seconds; the matcher would need engine-reported state at that cadence, which is exactly what in-engine schedulers get for free.
- A unit of account in tokens (input plus output, weighted) rather than core-seconds is needed for fair-share to be meaningful; HPC fair-share machinery (decayed usage, hierarchical accounts) transfers well if fed token usage.
- "Preemption" from an external scheduler can realistically mean only: cancel/requeue a call, or deny the next call of a low-priority program at a call boundary (the Maestro approach); token-level preemption requires engine integration.

### Gaps
- No published evaluation of backfill (EASY or conservative) applied to LLM request or agent-syscall queues was found.
- No measurements found of the snapshot/restore cost of AIOS's context interrupt in isolation (bytes saved, milliseconds per switch); only the end-to-end RR vs FIFO difference.
- No source quantified how loose `max_tokens` is as a runtime bound in agent workloads.

## 5. Costs and risks of a separate scheduler service

### Takeaway
Measured per-call costs of the building blocks are small relative to an LLM call (local gRPC about 0.1-0.3 ms; one Raft-replicated write about 1.6 ms unloaded and about 22 ms under heavy load; Kueue-style admission under 25 ms P99) but become material if every syscall incurs a consensus write, if the scheduler runs on periodic passes, or if the workload is tool-heavy with many short syscalls; the larger risks are structural (loss of engine-state visibility, preemption-induced memory blow-ups, and operating a separate HA control plane for a single-node workload).

### Cited Findings
- gRPC unary call over local IPC (2021 measurement): median about 167 microseconds client and server on the same core, about 116 microseconds on separate cores, vs 4-11 microseconds for raw Unix domain sockets. [search summary of an individual researcher's benchmark] — [gRPC for IPC](https://www.mpi-hd.mpg.de/personalhomes/fwerner/research/2021/09/grpc-for-ipc). About 300 microseconds on cloud VMs in a 2016 mailing-list report (rough). [search summary] — [grpc-io list](https://groups.google.com/g/grpc-io/c/FO2rZMJP6M4)
- etcd (Raft) write benchmark, v3.3 docs: single client, leader only, about 583 writes/s at 1.6 ms average latency; 1000 connections / 100 clients, about 44,000 writes/s at about 22 ms average. Commit latency is bounded by network round trip plus fdatasync: about 10 ms on spinning disk, often under 1 ms on SSD. [search summary of official docs; old version and hardware] — [etcd performance](https://etcd.io/docs/v3.3/op-guide/performance/). OpenShift guidance requires P99 fsync under 10 ms for etcd. [search summary; vendor doc] — [Red Hat etcd practices](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/etcd/etcd-practices)
- Kueue admission overhead below 25 ms at P99. [search summary; vendor research] — [Red Hat Research](https://research.redhat.com/blog/article/kubernetes-meets-genai-evaluating-performance-for-ai-inference-workloads/)
- Slurm-class per-task latency 2.2 s; default scheduling pass intervals 60 s (main) and 30 s (backfill). [search summaries] — [Reuther et al.](https://arxiv.org/pdf/1705.03102), [Slurm sched config](https://slurm.schedmd.com/sched_config.html)
- More elaborate policies cost scheduling time even in-process: Autellix and MLFQ "attain higher scheduling times than vLLM-opt's naive FCFS"; AIOS RR is 4% slower overall than FIFO (77.3 s vs 74.2 s) due to context-switch overhead. [full text] — [Autellix](https://arxiv.org/html/2502.13965v1), [AIOS](https://arxiv.org/html/2403.16971v4)
- Preemption risk: call-level MLFQ caused OOM at 4000 programs; KV swap overhead needed a custom kernel (swaps reduced up to 18x, swap time 3-7x, 1.3x throughput). [full text] — [Autellix](https://arxiv.org/html/2502.13965v1)
- Fairness-without-locality risk: up to 2.87x throughput loss (VTC vs DLPM). [abstract] — [DLPM](https://arxiv.org/abs/2501.14312)
- Central-component bottleneck precedents: Ray actor creation bounded by the GCS server [search summary] — [Ray forum](https://discuss.ray.io/t/performance-overhead-numbers/4208); YuniKorn docs attribute reduced throughput at 5,000 simultaneous pods to the API server becoming the bottleneck [search summary] — [YuniKorn KWOK](https://yunikorn.apache.org/docs/performance/evaluate_perf_function_with_kwok); Volcano's tuning guide reports the scheduling phase lagging pod creation at scale [search summary] — [Volcano tuning](https://volcano.sh/en/docs/user-guide/how_to_tune_volcano_performance)
- Agent-side integration risk: agents poll job state with conservative fixed waits rather than event subscription when driving Slurm/Flux, adding latency. [search summary] — [arXiv 2607.10081](https://arxiv.org/abs/2607.10081)

### Inferences
- Rough budget (my arithmetic from the figures above, not a sourced measurement): submit RPC about 0.1-0.3 ms + one replicated log write about 1-2 ms on SSD when unloaded + dispatch RPC about 0.1-0.3 ms gives roughly 1.5-3 ms per syscall if every state transition is committed through Raft, rising to tens of milliseconds under write contention. Against AIOS's measured 3-10 s agent waiting times and multi-second LLM calls this is under 1%; against fast tool/memory/storage syscalls (sub-millisecond to a few ms) it could dominate. Implication: route only LLM and heavyweight tool syscalls through the external scheduler, or replicate leases/quotas rather than individual syscalls.
- The Raft write-rate ceiling in the unloaded single-client case (about 583 serial writes/s) is in the same range as the syscall rates a large AIOS instance might generate; batching log entries is required if per-syscall durability is wanted.
- HA for the scheduler buys little if the LLM engine or the AIOS kernel is itself a single point of failure; it matters for multi-node, multi-tenant deployments.
- An external scheduler cannot see the engine's running batch or KV residency unless the engine exports it; without that, the evidence predicts it can deliver ordering/fairness/quota benefits (Autellix's 1.5-2x "program-level" increment over an engine-aware baseline, VTC-style fairness, AgentRM-style admission) but not the engine-level gains, and naive policies can be net negative (MLFQ OOM, locality loss).
- Expected-benefit map: likely positive for multi-tenant fairness and quotas, program-level priority across many agents, multi-engine/multi-GPU placement with locality and memory awareness, tool/sandbox resource admission, rate-limit-aware admission, mixed interactive plus batch agent workloads (QLM-style). Likely neutral for a single engine with homogeneous agents (AIOS's own test bed: FIFO vs RR about 4% apart). Likely negative for per-syscall round trips on short syscalls, periodic-pass scheduling, estimate-driven backfill at call granularity, and preemption without KV-memory awareness.

### Gaps
- No published measurement of gRPC plus Raft overhead in a scheduler hot path for LLM or agent workloads; the 1.5-3 ms figure above is an estimate and should be replaced by a benchmark of the actual system.
- gRPC and etcd figures are old (2016-2021, etcd v3.3) and hardware-specific; no Rust-specific (tonic/openraft) latency numbers were collected.
- No data found on WASM policy-plugin call overhead in a scheduling loop.
- No quantified operational-complexity cost (staffing, incident rates) for running a separate HA scheduler service was found; statements on that are inference only.
- Tool limitation: one direct fetch tool could not reach arxiv.org in this session (network allow-list); all arXiv content was retrieved through the alternate fetch tool, mostly abstracts. Full-text verification was done only for AIOS and Autellix.
